Capstone Project

Context

What this module solves

The five previous courses taught how to obtain a result. This one teaches how to make that result reach someone, which is a different problem and one where a lot of good work gets lost.

The module brings two things: what is expected of a Capstone project, and how a finished analysis becomes something a stranger reads in two minutes and wants to ask you more about.

And a clarification from the page itself, because it changes how you approach it: the Capstone project is optional, and it brings together concepts from the six previous courses on a new scenario, Salifort Motors. Its lab lives behind the login, so that one you do on the platform. What gets built here is the other half: the packaging.

Example

Before the theory: a toy example

No need to invent one: it is in your library. We take a single finding, the one from the Waze project of Course 5, and measure what it turns into depending on the size of the document.

Step 1. Count what there is

The script wrote a results file. Inside it there are:

numbers saved by the script   =  69

Sixty-nine figures: partition sizes, metrics of every model, chosen knobs, search times, importances of nine variables. All verified, all publishable.

Step 2. Count what survives at each size

Now the four documents that tell that same finding, measured:

DocumentWordsFigures it quotes
One sentence111
Executive summary80435
Case sheet1,20028
PACE report7060
The results file(not prose)69

Step 3. Read the table, which says three things

The first: from 69 to 1. The funnel is brutal, and it is not a flaw. If the sentence quoted all sixty-nine, it would not be a sentence.

The second: the sheet is longer than the summary and quotes fewer figures. 1,200 words against 804, and 28 figures against 35. It is not carelessness: they do different jobs. The summary is dense because whoever reads it wants the numbers; the sheet is long because whoever reads it wants to understand why those numbers, and that is told with sentences, not with data.

The third, and it is the best one: the PACE plan quotes zero figures. Not one, in 706 words. And it cannot be any other way, because it is written before there are results. It is the document that says what you expect to find, and an expectation written after seeing the result is not an expectation.

Step 4. The 11-word sentence

Tuning the forest almost closes the gap and does not close it.

Eleven words and one implied figure. That is what someone is going to remember from a project that cost three grid searches, 88 combinations of knobs and five figures.

If that sentence does not exist, the project is not finished. It has stopped.

Terms

Glossary

  • Capstone project. The final project of the certificate, optional, which brings together concepts from the six previous courses on a new scenario.
  • Portfolio. The collection of work you show so that someone decides whether to talk to you. It is not a repository: it is a selection.
  • Executive summary. One or two pages with the result, the decision and the limits. Read by whoever pays.
  • Case sheet. The story of the analysis: what was asked, what was found and why it can be believed. Read by whoever doubts.
  • PACE plan. The strategy document, written before analysing. Plan, Analyze, Construct, Execute.
  • Results file. The JSON the code writes with every publishable number. It is the only source the figures of the other documents can come from.
  • Résumé. A one- or two-page document whose job is to get a conversation, not to describe your life.
  • Applicant tracking system. The program that reads your résumé before a person does. ATS for short.
Method

Step by step

Step 1. Write the sentence before anything else

When the analysis is finished, the first thing written is the sentence. If it does not come out, or comes out convoluted, the analysis has not reached a conclusion yet.

Three tests to know whether the sentence works:

  1. Does it fit on one line? Eleven words is a good target.
  2. Does it change a decision? "The forest does not win" changes what gets deployed. "The hyperparameters were tuned" changes nothing.
  3. Is it understood without the rest of the document? If it needs context, it is not the sentence.

Step 2. Build the layers outwards

From the sentence you work outwards, not the other way round:

LayerWho reads itWhat you give them
One sentenceWhoever decidesThe result
Executive summaryWhoever paysThe numbers and the decision
Case sheetWhoever doubtsWhy it can be believed
PACE planWhoever auditsWhat you expected before looking
Script and notebookWhoever reproducesEverything

All five tell the same story. If the sentence and the report do not agree, the problem is not one of format.

Step 3. The rule that makes contradiction impossible

No document quotes a figure that is not in the results file. That rule is what prevents the summary from saying 0.7379 and the sheet 0.7348 because someone re-tuned something and forgot a paragraph.

It is not bureaucracy: it is the difference between a portfolio that survives being looked at and one that falls over at the second question.

Step 4. What makes a portfolio project good

It is not the model. It is this, and in this order:

  1. A question someone had. "Predict churn so we can act before it happens" is a question; "apply random forest" is an exercise.
  2. A decision that changes with the answer.
  3. A defensible number, with its test set looked at exactly once.
  4. What did not work, in the same detail as what did.
  5. The limits, written by you before someone else finds them.

Look at the fourth one. A project without a single dead end does not look flawless, it looks incomplete, and whoever interviews you notices.

Step 5. Communicating what you can do, which is not the same as listing it

Before the résumé there is a step the module treats separately: knowing how to say what you can do. And the trap is that the list of tools does not say it.

"Python, SQL, scikit-learn" is an inventory. What someone needs to know is what problem you solve with that, and that is told in three pieces:

PieceWhat it isYour example
The skillWhat you know how to doComparing a model against an honest baseline
The edgeWhy youYou come from operating processes, so you ask where the data came from
The proofWhere it showsThe project where one question tied with three hundred trees

Without the third, the first two are a claim. With it they are a verifiable fact, and the conversation stops being about whether you know and turns to what you did.

And there is an edge of yours worth not hiding: you do not come from computer science. Someone who has run a plant knows that an impossible value exists and that an average hides a drift. That, in this library, already produced the finding of the 461 users who drive the impossible, which no later course had flagged.

Step 6. The résumé, which is another document with the same logic

A résumé does not describe your life: it gets a conversation. And a program reads it first, so there are two readers with different needs.

For the programFor the person
The words of the job ad, verbatimA result with a number
Plain text, no columns or odd tablesA sentence that gets remembered
A format it knows how to readReadable in seven seconds

And the rule that orders the content: every line is a result, not a task. "Responsible for the churn analysis" is a task. "Churn model on 14,299 users that identified the threshold as the real cause of the 8% detection rate" is a result.

Yours are already measured and written. It is a matter of lifting them out of the report.

Code

The code, in parts

Step 1. Measure the funnel of your own project

The toy example, done by the machine.

import json
import re
from pathlib import Path

report = Path("projects/curso5/waze/04_reports/model_results.json")
summary = Path("projects/curso5/waze/04_reports/executive_summary.md")

def stored(node):
    """Every number the script wrote, however deep it sits."""
    if isinstance(node, dict):
        return set().union(*(stored(v) for v in node.values())) if node else set()
    if isinstance(node, list):
        return set().union(*(stored(v) for v in node)) if node else set()
    if isinstance(node, bool) or not isinstance(node, (int, float)):
        return set()
    return {float(node)}

numbers = stored(json.loads(report.read_text(encoding="utf-8")))
cited = set(re.findall(r"0,\d{3,4}", summary.read_text(encoding="utf-8")))
print(f"guardados por el guion: {len(numbers)}")
print(f"citados en el resumen:  {len(cited)}")
line by line
def stored(node):
A recursive function: it calls itself. It is needed because the JSON has dictionaries inside dictionaries and there is no knowing in advance how many levels there are.
set().union(*(...))
The asterisk unpacks: it turns a list of sets into separate arguments for union. Without it you would pass one argument that is a list, and it would fail.
if ... else set()
The guard for an empty dictionary. union() with no arguments raises an error, so an empty node returns the empty set.
isinstance(node, bool)
Checked before the number, because in Python True is an integer worth 1. Without this line, every true in the JSON would count as the number 1.
re.findall(r"0,\d{3,4}", ...)
Looks for figures written the Spanish way, with a comma. \d{3,4} is three or four digits. The r in front saves writing the backslash twice.
set(...)
Turns the list into a set, so a figure repeated in two paragraphs counts once. That is what we want: it measures how many distinct figures are quoted.
prints
guardados por el guion: 69
citados en el resumen:  35

Sixty-nine saved, thirty-five quoted. Half of the measured work does not appear in the summary, and it is right that it does not: it is there for when someone asks.

line by line
courses = {...}
A dictionary acting as a translation table, from folder name to readable label. Keeping that pair together avoids scattering the correspondence across the code.
for folder, label in courses.items()
items() walks key and value at once. Without it you would have to look up the value inside the loop.
path.exists()
Asks the disk whether the file is there. It is what turns "which courses touched this case" into something checked instead of remembered.
row.append(label if path.exists() else " - ")
A one-line conditional. The spaces around the dash are there so the columns line up when printed.
' '.join(row)
Glues the elements of the list with a space between them. It is the normal way to print a row.

Traps

Watch out

  • If you cannot write the sentence, the analysis is not finished. It is not a writing problem.
  • A portfolio that only shows successes looks incomplete. What did not work is what proves you can tell the difference.
  • Nobody is going to read your notebook. It is the support, not the deliverable.
  • A figure that appears in two documents with two values destroys trust in both. That is why everything comes out of a single file.
  • The PACE plan is written before. Writing it afterwards is inventing an expectation you already know came true.
  • Repeating the tutorial is not a project. If you use the course datasets, ask a question the exemplar did not ask.
  • Metrics without a decision say nothing. An AUC of 0.86 is not a result; "we contact the 20% at highest risk and recover 62%" is.
Analogy

Metallurgical bridge

The report of a test campaign has exactly these layers, and you have already seen them ordered this way.

In the certificateIn the campaign report
One sentenceThe recommendation, on the cover
Executive summaryThe summary for the committee
Case sheetThe body, with the conditions and why they were chosen
PACE planThe test program, signed before starting
Script and notebookThe annexes with the balances and the test sheets

And the parallel holds down to the uncomfortable detail. The test program is signed before the tests are run, just as the PACE plan quotes not a single figure. A program written at the end, with the winning conditions already set down as if they had been foreseen, fools nobody who has run a campaign.

And the tests that went wrong go in the body, they are not thrown away. A report that only shows the winning conditions leaves the reader without knowing what was tried and did not work, which is half of the useful information for whoever comes next.

The difference is in who reads. At the plant the committee knows the process; in a portfolio the reader does not know you, so the sentence on the cover has to work even harder.

Review

Review

Why does the PACE plan of the Waze project quote zero figures in 706 words?

Because it is written before analysing. Its job is to set down in writing what is going to be done and what is expected to be found, and at that moment there are no results to quote. That is exactly what gives it value afterwards: when the project ends, you can check whether what happened resembles what was expected, and that check is only worth something if the expectation was written beforehand. A plan drafted at the end, with the conclusions already known, is not a plan but a rationalisation.

The executive summary has 804 words and quotes 35 figures; the sheet has 1,200 and quotes 28. Why does the longer one quote fewer?

Because they do different jobs. The summary is read by whoever decides and wants the numbers, so it is short and dense. The sheet is read by whoever doubts and wants to understand why those numbers are credible, and that is explained with sentences: how the data was split, what was discarded and why, what did not work. More words per figure is not padding, it is the explanation that turns a number into something defensible.

What separates a résumé line that works from one that does not?

That it describes a result instead of a task. "Responsible for the churn analysis" says what you were assigned; "churn model on 14,299 users that identified the threshold as the real reason only 8% were detected" says what you achieved, with a figure that can be asked about. And there is a second reader before the person: the program that filters résumés, which needs the words of the job ad verbatim and a plain format it knows how to read.

Why is a project that only shows what went well worse than one that shows the failures?

Because real work produces dead ends, and a portfolio without any can only mean two things: that the project was trivial or that they have been hidden. Both count against you. Telling what did not work proves you can tell a result from an artefact, which is the skill being evaluated. In the projects of this library that is half of the content: a segmentation that found no groups, a model that ties with a single question, a brief that cannot be fulfilled with the data available.

Why do all published figures have to come out of a single results file?

So that it is mechanically impossible for two documents to contradict each other. If the summary says 0.7379 and the sheet says 0.7348 because someone re-tuned something and updated one file but not the other, whoever reads them stops trusting both, and rightly so. By writing the code so that it saves everything publishable in one place, and forbidding yourself from quoting anything that is not there, the problem disappears instead of depending on remembering.
