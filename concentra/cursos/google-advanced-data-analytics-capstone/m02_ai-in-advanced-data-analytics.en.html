Context

What this module solves

This is the only block of the Capstone with new content, and it is about using a generative model as an analysis tool: cleaning data, building formulas, sharpening questions and explaining charts.

The problem is not whether it helps. It helps a lot with some things and does harm with others, and the boundary is not a matter of opinion: it gets calculated. This module puts that arithmetic up front and then teaches the only defence that works, which is checking instead of trusting.

Example

Before the theory: a toy example

The model takes one minute to answer, always. The question is not whether it gets it right: it is whether it pays off. And it pays off when checking the answer costs less than having done it yourself.

Step 1. The arithmetic, with five tasks

For each one, how long it takes you by hand and how long it takes to check what it gave you:

TaskBy handCheckingSaving
Writing the code that parses some dates20 min2 min+17 min
Explaining an error message10 min1 min+8 min
Proposing three approaches you had not thought of30 min5 min+24 min
Computing the median of a column1 min1 min−1 min
Saying whether a difference is significant5 min5 min−1 min

The saving is what you take by hand minus what you take using it, which is one minute of waiting plus what checking costs:

saving = by hand − (1 + checking)

dates:         20 − (1 + 2) = +17
median:         1 − (1 + 1) = −1
significance:   5 − (1 + 5) = −1

Step 2. Look at why the last two come out negative

It is not that the model is worse at those tasks. It is that checking them is doing them.

To know whether the median it gave you is right, you have to compute the median. To know whether that difference is significant, you have to run the test. As soon as the check is the whole job, the model cannot save anything, only add a minute.

And at the top the opposite happens. Checking a date parser is running it on five cases you already know: two minutes against the twenty of writing it. That is where all the value lives.

It is good for what you can check cheaply. It is not good for what you would have to take on faith.

Step 3. What if I do not check?

It is the obvious temptation, so it gets its arithmetic too. Suppose checking costs 5 minutes and a wrong number inside a delivered report costs 240 minutes between redoing it and the lost credibility.

Not checking only comes out cheaper if the model is wrong very rarely:

not checking pays off  if   probability of failure × 240  <  5

                            probability of failure  <  5 / 240  =  0.0208

2.08%. In other words, for not looking to pay off, the model would have to get concrete figures right 97.9% of the time.

None of them does, and that is the whole argument. There is no need to debate whether models hallucinate or not: with these numbers, it is enough for them to fail one time in fifty for not checking to be the worst deal in the table.

Terms

Glossary

  • Generative model. The kind that produces text by predicting which word comes next. It does not compute: it generates something that looks like an answer.
  • Hallucination. A false answer said with the same confidence as a true one. It is not a rare failure of the model: it is how it works when it does not know.
  • Prompt. What you ask it, with its context.
  • Verification cost. How long it takes you to check the answer. It is the only figure that decides whether the tool is useful for that task.
  • Known case. An input whose correct answer you already know, and which therefore serves to audit any code you are handed.
  • Test bench. A handful of known cases running together. It is the cheap way to verify generated code.
  • Format inference. When a library guesses how your data is written instead of being told. It is convenient and it is where silent errors hide.
Method

Step by step

Step 1. Classify the task before asking for anything

Kind of taskUseful?Why
Writing repetitive codeYesYou check it by running it
Explaining an errorYesThe explanation is verified when you fix it
Proposing approachesYesYou evaluate them, and it widens what occurs to you
Drafting a textYes, with reviewThe numbers you put in yourself
Explaining what a chart showsWith careIt describes well; it concludes badly
Computing a numberNoIt does not compute, it predicts text that looks like a number
Saying whether something is significantNoThat comes out of your data, not its training
Remembering what is in your fileNoIt has not seen it, and it will answer anyway

The charts row deserves its nuance, because it is the activity the module proposes. A model correctly describes what can be seen: two peaks, a long tail, a gap. And it makes up why, because the why is not in the picture. The first saves work; the second is exactly what must not get into a report.

Step 2. Give it context instead of asking it to guess

It is the practical difference between a useful answer and an invented one.

Bad: "I have a column of dates that does not parse well, what do I do?"

Good: paste five real values from the column, the full error message and which version of pandas you use.

In the first case it has to imagine your data, and it does. In the second it has the data in front of it.

Step 3. Ask for the reasoning, not just the result

Reasoning can be audited by reading; a bare number cannot be audited in any way. If it gives you the steps, you can see where it goes wrong without redoing the whole calculation.

Step 4. Use it to sharpen the question, which is its best use

This is the use the module highlights and the one most often wasted. Not to answer: to improve the question before spending a day answering it.

The technique is to ask it to attack the question:

"I want to predict which user abandons the app with these columns. Tell me which questions I should ask myself before starting and what can go wrong."

And it works because a critique evaluates itself. If it tells you to check whether the missing labels look like the rest, or whether some variable would not exist at prediction time, you can look at that in your file in five minutes. If it says something silly, it gets discarded and has cost nothing.

Three questions worth always asking it before an analysis:

  1. Which variable in this list would not exist at prediction time? It is the question that catches information leaks, and in the Automatidata project of Course 5 the total amount contained the tip.
  2. What alternative explanation would this result have? It forces you to name what would have to be ruled out.
  3. What would it take for this conclusion to be false? It turns a hunch into something checkable.

Notice that none of the three asks for a piece of data. They ask for approaches, which is the row with the biggest saving in the example's table: half an hour of thinking against five minutes of discarding.

Step 5. Check with known cases, which is the module's technique

For code, cheap verification has a name and is always the same: a handful of inputs whose answer you already know.

No test framework needed. Five cases, the correct answer next to each, and a function that counts the failures. It is what turns "it seems to work" into "it fails on 1 of 3, and it is precisely the ambiguous date".

Step 6. And what does not change because you use a model

You still sign. If the code it gave you has an information leak, the leak is yours. If the chart it suggested misleads, it misleads with your name on it.

From that comes the only rule to remember: if you cannot explain a line, it does not go into a deliverable. The annotation blocks in these lessons exist for exactly that.

And one that is always forgotten: what you paste, you publish. A company's data, a file with people in it or a key do not get pasted into an external service.

Step 7. And where to go from here

The module closes by recommending Google AI Essentials, which is a separate Google course on the foundations of generative AI: what it is, how useful prompts are written and what responsible considerations it brings. It is not part of this certificate, so here it only stays noted as the next step the platform proposes.

And an honest reading of that recommendation: what this module teaches is already the part that matters to an analyst, which is the arithmetic of when it pays off and the habit of checking. The rest is handling the tool, and that is learned by using it.

Code

The code, in parts

Step 1. The same date, two different answers

This is not a made-up example: it is the ambiguity your own Course 2 project flagged in the taxi file, where dates come as MM/DD/YYYY.

import pandas as pd

AMBIGUA = "09/01/2017"

for antes, despues in [("03/25/2017", "12/31/2017"), ("25/03/2017", "31/12/2017")]:
    columna = pd.to_datetime(pd.Series([antes, AMBIGUA, despues]))
    print(f"con {antes} al lado  ->  {AMBIGUA} es {columna[1].date()}")
line by line
AMBIGUA = "09/01/2017"
A date that can be read two ways: September 1 if the month goes first, January 9 if the day goes first. In capitals by convention, because it is a constant that does not change.
[("03/25/2017", ...), ("25/03/2017", ...)]
Two pairs of neighbours. The first only makes sense with the month first, because there is no month 25. The second only with the day first.
pd.Series([antes, AMBIGUA, despues])
The ambiguous one goes in the middle on purpose. If it came first, pandas would fix the format from it and the example would teach nothing.
pd.to_datetime(...)
Without telling it the format. That is how anyone in a hurry would write it, and it is the line a model will give you if you do not say more.
columna[1].date()
The second element, which is the ambiguous one, and only its date without the time.
prints
con 03/25/2017 al lado  ->  09/01/2017 es 2017-09-01
con 25/03/2017 al lado  ->  09/01/2017 es 2017-01-09

The same string of text, two different dates, and no error. Pandas looks at the neighbours, infers the format and applies that inference to all of them. Change the neighbours and the answer changes.

A model that writes pd.to_datetime(columna) for you is not wrong: it is writing the reasonable thing without knowing what is in your file. The error is introduced when you accept it without checking.

Step 2. The test bench that catches it

Three cases with their known answer, and a function that audits any parser.

CASOS = [("03/25/2017", "2017-03-25"),
         ("09/01/2017", "2017-09-01"),
         ("12/31/2017", "2017-12-31")]

def auditar(parsear, nombre):
    fallos = [texto for texto, correcta in CASOS
              if str(parsear(texto).date()) != correcta]
    print(f"{nombre:24} falla en {len(fallos)} de {len(CASOS)}  {fallos}")

auditar(lambda t: pd.to_datetime(t, dayfirst=True), "inferido dia-primero")
auditar(lambda t: pd.to_datetime(t, format="%m/%d/%Y"), "formato declarado")
line by line
CASOS = [(entrada, respuesta), ...]
The key piece: each input with the answer you already know. Without that second column there is no verification possible, only an impression.
def auditar(parsear, nombre):
The function receives another function as an argument. In Python functions are ordinary values, and that lets you audit any parser with the same bench.
[texto for texto, correcta in CASOS if ...]
A list comprehension with a filter: it walks the pairs and keeps only the inputs whose answer does not match.
str(parsear(texto).date())
Converts to text so it can be compared with the written answer. Comparing date objects against strings would always be false, without warning.
lambda t: pd.to_datetime(t, ...)
An anonymous one-line function, to wrap each variant and pass it to the auditor. It exists only for the duration of the call.
{nombre:24}
Reserves 24 spaces for the name, so the two output lines line up and can be compared at a glance.
prints
inferido dia-primero     falla en 1 de 3  ['09/01/2017']
formato declarado        falla en 0 de 3  []

Three cases and two minutes have turned a doubt into a fact: the first one fails, and it fails precisely on the ambiguous date, the one that was going to spoil the analysis without saying anything.

That is the +17 minutes of saving from the example's table, collected.

Traps

Watch out

  • It does not compute. It predicts text that looks like an answer. A number it gives you without running code is a guess in the shape of a result.
  • A silent error is worse than a noisy one. The badly parsed date raises no exception: it yields a wrong analysis, months later.
  • errors="coerce" fixes nothing, it turns what fails into missing. If a model proposes it to get rid of an error, it is proposing to hide rows.
  • It describes a chart well and concludes badly. The why is not in the picture.
  • If checking costs the same as doing it, do not use the tool. That is the example's table, and it admits no exceptions.
  • Do not ask it what is in your file. It has not seen it, and it will answer anyway.
  • What you paste, you publish. Other people's data and keys, never.
  • You sign. Generated code that ends up in your report is yours, leaks included.
Analogy

Metallurgical bridge

A generative model is a brilliant, very articulate intern in their first week.

They know a huge amount in general, have read every manual, and do not know your plant. You ask them how to adjust the pH of a circuit and they give you a well-built, coherent, plausible answer, without ever having seen your ore.

From that comes exactly the same division of tasks as the example's table:

To the internTo the model
"Set up the test rig", which is checked by looking at itWriting code, which is checked by running it
"Find me what the manual says about this reagent"Explaining an error or a function
"What would you try?", which you evaluateProposing approaches
Never: "what was the recovery of the shift?"Never: a concrete number

And that last row is the one that really costs money. An intern who does not know the recovery of the shift will tell you they do not know. The model will not: it will give you a plausible figure, with two decimals, and in the same tone it used for the good answer before.

That is the whole difference and why you have to check: it does not tell not knowing from knowing, so that distinction has to come from you.

Review

Review

Why does using the model to compute a median come out with a negative saving?

Because to check that the median it gave you is right you have to compute the median, and as soon as the check is the whole job the model cannot save anything. The arithmetic makes it plain: one minute of waiting plus one minute of checking against the minute it cost to do it, in other words one minute lost. It is the same reason that asking it whether a difference is significant does not pay off either. And the other way round, writing a date parser is checked in two minutes by running it on known cases against the twenty of writing it, and there the saving is seventeen real minutes.

What probability of being right would it take to justify not checking?

97.9%. It comes from comparing the two costs: checking costs 5 minutes and a wrong number inside a delivered report costs about 240 between redoing it and the lost credibility, so not checking only pays off if the probability of failure is smaller than 5 divided by 240, that is 2.08%. The interesting thing about the calculation is that there is no need to debate how much a model hallucinates: with such an asymmetric cost of error, it is enough for it to fail one time in fifty for skipping the check to be the worst option in the table.

The same date comes out as September 1 or as January 9. What is going on and why is it dangerous?

Pandas does not know whether the month goes first or the day, so it infers it by looking at the rest of the column and applies that inference to every value. With 03/25/2017 next to it only month-first fits, because there is no month 25, and the ambiguous one comes out as September 1; with 25/03/2017 next to it the inference flips and it comes out as January

  1. It is dangerous because it raises no error: the program goes on, the analysis gets

done, and the mistake shows up months later or never. The fix is to declare the format instead of letting it be guessed.

A model correctly describes a chart. Can that description be used in a report?

The description yes, with review: saying there are two peaks separated by a gap or that the tail stretches to the right is reading the picture, and that is checked by looking at it. The conclusion no. Why there are two peaks is not in the picture, it is in the process that generated the data, and the model does not know it, so it is going to invent it with the same confidence. In practice it serves to speed up the figure caption and never to write the results section.

Why is an intern in their first week a better analogy than a calculator?

Because a calculator rarely gets it wrong and warns when it cannot do something, and a model does the opposite: it is tremendously capable in general and does not tell not knowing from knowing. An intern who does not know the recovery of the shift will tell you they do not know; the model will give you a plausible figure with two decimals and the same confident tone it used for the good answer before. That is why the division of tasks is the same as with a new person: they get assigned what is checked by looking at it, and never a concrete figure from your process.
