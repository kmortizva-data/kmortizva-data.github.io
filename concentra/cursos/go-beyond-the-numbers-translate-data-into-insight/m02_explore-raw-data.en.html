Explore raw data

The five lines to run before having an opinion about a file, and the three traps they uncover, a grade that sorts wrongly for being stored as text, some dates that put November before September, and a histogram that tells two different stories depending on how many bars you give it.

Context

What this module solves

You have a file and you have never seen it. The question is not yet what to conclude, but what is in there: how many rows, which columns, what the computer thinks each one is and what is missing.

It is the part of the work that is not taught and where the expensive mistakes slip in, because none of them produces an error message. A number stored as text sorts wrongly in silence. A date written as text puts November before September. A histogram with few bars turns three groups into one.

This module is the procedure so that none of those three things happens to you without you noticing.

Example

Before the theory: a toy example

Six laboratory samples, just as they arrive from the system:

sampletaken_ongradeshift
M-1019/1/202628.4dia
M-1029/15/20269.7noche
M-10310/1/202631.2dia
M-10410/20/2026(empty)noche
M-10511/3/202630.5dia
M-10611/28/202629.8noche

Six rows and four columns. It looks as if there is nothing to discover. There are three things.

Step 1. The grade is stored as text

If the file brings the grades in quotes, the computer sorts them as words, letter by letter. And comparing letter by letter, 9 is greater than 2:

ordenadas como texto:    28.4   29.8   30.5   31.2   9.7
ordenadas como número:    9.7   28.4   29.8   30.5   31.2

The lowest grade of the lot, which is exactly the one to look at, goes to the end of the list. If you look for the minimum by looking at the first sorted value, you walk away with 28.4.

Step 2. The dates are text too

And with the same letter-by-letter criterion, 1 goes before 9:

ordenadas como texto:    10/1/2026   10/20/2026   11/28/2026   11/3/2026   9/1/2026   9/15/2026
ordenadas como fecha:    2026-09-01  2026-09-15   2026-10-01   2026-10-20  2026-11-03  2026-11-28

Two disasters in a single line: October and November go before September, and within November, the 28th goes before the 3rd. Any trend analysis done on that column without converting it is looking at a scrambled time series.

Step 3. A value is missing, and that changes a mean

Sample M-104 has no grade. When grouping by shift:

turno    muestras    ley media
día          3         30,03
noche        2         19,75

Two things have to be said about that table, and both belong to the module:

  • The night mean comes out of two samples, not three. The gap raises no error, it only shrinks the denominator without warning.
  • That 19.75 describes no sample: it is the average of 9.7 and 29.8. The grade of 9.7 is the real finding, and the average hides it.

Step 4. And a fourth one, with other data: how many bars the histogram has

Twelve recoveries of a circuit:

61  62  63  64      71  72  73  74      81  82  83  84

With three bars:

[4, 4, 4]        bordes: 61,0   68,7   76,3   84,0

A flat split, perfectly boring. With six bars:

[4, 0, 2, 2, 0, 4]    bordes: 61,0  64,8  68,7  72,5  76,3  80,2  84,0

Three groups separated by gaps appear. It is the same data. And the mean is 72.5, which falls inside the middle group: it describes four of the twelve measurements and says nothing about the other eight.

Terms

Glossary

  • DataFrame. The pandas table: rows, named columns and one data type per column.
  • Data type. What the computer thinks each column is: integer, decimal, text, date. dtype for short, and it is the first thing to check.
  • Object or text. The type pandas assigns when it does not recognise numbers. **A numeric column marked as text is the most common failure when opening a file.**
  • Null value. The empty cell, which pandas writes as NaN. It is not a zero: it is an "I do not know", and treating it as zero changes every mean.
  • Datetime. The data type for dates and times. Converting text to datetime is what allows sorting, subtracting and grouping by month.
  • ISO format. Writing a date as 2026-11-03, year, month and day. It has a practical virtue: sorted as text it comes out the same as sorted as a date, because the big parts go first.
  • Discovering. The practice of the previous module applied here: getting to know the shape, size and content.
  • Structuring. Reorganising the raw data: sorting, grouping, pivoting, splitting columns.
  • Grouping. Splitting the table by the values of a column and calculating something inside each part. groupby in pandas.
  • Histogram. A chart that splits the values into intervals and counts how many fall in each one. The number of intervals is your decision and it changes what it seems to say.
  • Data provenance. Where it came from: who measured it, with what and when. It determines what can be trusted.
Method

Step by step

Step 1. Ask where the data comes from

Before the first line of code, and it is not a formality. Data collected by hand, data that comes out of a sensor and data that comes from a form a customer fills in have different errors, and looking for the ones that are not there is a waste of time.

Where it comes fromWhat fails there
Typed in by handTypos, mixed units, empty cells
Automatic sensorRuns of repeated values, gaps from outages, drifts
User formBlank answers, free text where there should have been an option
Another system, already aggregatedYou already lost the spread inside and cannot get it back

The last row is the most important and the least obvious: if you are handed means per shift, there is no way of knowing whether there was variability within a shift.

Step 2. The ritual of the five lines

Always the same five, always in this order:

LineWhat it answersWhat you are looking for
df.shapeThe size of the problemIs it 500 rows or 700,000?
df.info()Types and non-nulls at onceNumeric columns marked as text
df.describe()Minimum, maximum, meanImpossible values, not striking ones
df.head(10)What a real row looks likeWhat no summary shows
df.isna().sum()Where the gaps areWhether they concentrate in one column or in a few rows

About describe(), the right question is not which numbers come out. It is which ones are impossible: a negative fare, a grade of 150%, an age of 200 years, a date in 1970 in this year's data.

Step 3. Fix the types before touching anything else

Two conversions and in that order, because everything else depends on them:

  1. The numbers to number, with pd.to_numeric.
  2. The dates to date, with pd.to_datetime telling it the format.

The format matters: 9/1/2026 can be September 1 or January 9, and the difference between the two readings is not settled by anyone guessing. It is said explicitly with format="%m/%d/%Y".

And once the column is a date, what was needed opens up: extracting the month, subtracting two dates to get a duration, grouping by week.

Step 4. Structure so that the story appears

Four operations that cover almost everything:

OperationWhat for
Sort by a columnSeeing extremes and trends
Group and summariseComparing segments
FilterIsolating the piece that matters
PivotCrossing two variables in a table

And the rule of the previous module still stands: after each one, validate. Are they still the same rows? Does the count per group add up to the total?

Step 5. Draw the histogram more than once

The number of bars is not an aesthetic detail, it is an analytical decision. The healthy habit is to try three cuts before concluding anything about the shape:

  • Few bars flatten the story and merge distinct groups into one.
  • Too many turn noise into peaks that look meaningful.
  • The useful point is usually where the shape stops changing when one more bar is added.

And one check that is worth many: look at whether the mean falls where there is no data. If so, you have more than one group and the mean describes nobody.

Traps

Watch out

  • A numeric column stored as text sorts wrongly and does not warn. The 9.7 goes to the end. Checking the types with info() is the first line of defence.
  • A date as text puts November before September. And the 28th before the 3rd.
  • When converting dates, tell it the format. 9/1/2026 is ambiguous and guessing it produces analyses with the months swapped.
  • count counts non-nulls, not rows. It is what gives away that a mean came out of less data than you think.
  • A gap is not a zero. Treating it as zero lowers every mean without anything complaining.
  • describe() only looks at the numeric columns by default. The text ones, with their unexpected categories, have to be asked for separately.
  • The number of bars of a histogram changes the conclusion. Try three cuts before talking about the shape.
  • A mean can describe a small part of the set. With three groups, the 72.5 of the example portrays four measurements out of twelve. If the histogram shows groups, they are reported separately.
  • info() is not printed with print. It writes on its own and returns nothing.
Analogy

Metallurgical bridge

The ritual of the five lines is the inspection of the sample before sending it to the laboratory, and you do it without thinking: how many bags arrived, whether they come labelled, whether the weight matches the dispatch note, whether any came wet.

Nobody sends a lot for analysis without looking at the bags. This module is the same thing with a file.

At the plantIn the file
Counting the bags that arriveddf.shape
Checking that they all carry a labeldf.info(), the types
Looking for the bag without a labeldf.isna().sum()
Seeing whether any weight is impossibledf.describe(), minimums and maximums
Opening one and looking at itdf.head(10)

And the three traps have their exact equivalent:

The grade stored as text is the certificate that arrives with the decimal comma where the point goes, and that on importing turns a 2.5% into a 25%. It has happened in real plants.

The scrambled dates are the log filed by file name instead of by date, with November in front of September.

The histogram with few bars is the particle size analysis with too few sieves: if you skip meshes, two populations of particles merge into a single fraction and the report says the grind is uniform when it is not. The resolution you measure with decides what you can see, and that holds equally for a sieve and for a histogram interval.

Review

Review

Why is it dangerous for a numeric column to be stored as text?

Because it sorts and compares letter by letter instead of by value, and gives no error. In the module's example, the grades sorted as text come out 28.4, 29.8, 30.5, 31.2 and 9.7: the lowest of the lot, which is precisely the one that had to be investigated, ends up last. Besides, it cannot be averaged or subtracted until converted. It is detected with df.info(), looking at the types column, and fixed with pd.to_numeric before touching anything else.

What are the five lines and what does each one look for?

df.shape gives the size of the problem, df.info() the types and the non-nulls at once, df.describe() the minimums and maximums where impossible values are looked for rather than striking ones, df.head(10) what a real row looks like, and df.isna().sum() where the gaps are and how many. They are always run in that order and before having any opinion about the file. The only one that tends to be misread is describe(): the question is not which numbers come out, but which are impossible for the phenomenon being measured.

When converting dates, why does the format have to be given?

Because a date like 9/1/2026 is ambiguous: it can be September 1 or January 9, and no universal rule settles it, since some countries write month then day and others the other way round. If it is not given, the library guesses, and if it guesses wrong the analysis comes out with the months swapped without any warning. It is said explicitly with format="%m/%d/%Y". As a habit, storing and writing dates in ISO format, 2026-11-03, avoids the problem at the root, because in that format the alphabetical order matches the chronological one.

The same data drawn with 3 and with 6 bars gives two stories. Which is the right one?

Neither of the two on its own: the conclusion is that several cuts have to be tried before talking about the shape. With 3 bars the twelve recoveries come out [4, 4, 4], a flat split with nothing to tell; with 6 they come out [4, 0, 2, 2, 0, 4] and three groups separated by gaps appear. Few bars merge distinct groups and too many turn noise into peaks. And the histogram with six lets you see something no summary says: the mean, 72.5, falls inside the central group, so it describes four measurements out of twelve and is silent about the other eight existing. When the drawing shows groups, they are reported separately.

Why does it matter to know where the data comes from before analysing it?

Because the origin determines which errors to look for, and looking for the ones that are not there is wasted time. Data typed by hand brings typos and mixed units; sensor data brings repeated runs and gaps from outages; form data brings blank answers and free text. And the most important case is data that arrives already aggregated: if you are handed means per shift, the spread that existed within each shift was lost and there is no way of recovering it, so there are questions that file can no longer answer however much it is analysed.
